# Recurring improvement

The user authorised recurring engineering review, improvement and distinct releases of this project. The active Codex thread heartbeat is **Airspace product improvement**, identifier `airspace-product-improvement`, scheduled **every six hours**. It reviews the current project and its existing GitHub, Hugging Face and System Lab publications. It does not schedule aircraft operations.

The durable prompt is [improvement/RECURRING_PROMPT.md](../improvement/RECURRING_PROMPT.md). Each run reads the original baseline, revision addenda, current status, previous cycle record and release evidence, then selects a bounded concrete improvement. The normal run budget is 45 minutes of active work and two actual local-model evaluation calls. Larger work is checkpointed instead of represented as finished.

A run must inspect the actual interface, repair meaningful defects, improve operator guidance, review animation and reactive background, remove slogans and formulaic presentation, verify tenant/actor privacy and server-enforced action controls, and record exact tests and actual model evidence. It must preserve original source/legal material, technical identifiers and essential safety meaning. It must keep the owned companion animated in normal motion settings and honour pause/reduced-motion preferences.

New candidate releases are permitted only after relevant software, rights, security, installation and publication gates pass. Existing tags/assets stay frozen. A successful upload is not a successful publication: independent retrieval and digest/content checks remain required. Model cards and datasets must describe actual artifacts and measured results. No simulated operator/customer records, fabricated training, legal claims or telemetry are permitted.

The cycle cannot email, contact people, buy services, submit to an authority, activate an external flight/provider service, command aircraft, grant permissions or alter its own approval boundaries. It stays quiet when nothing meaningful changes and reports a verified improvement/release, failure or required user action. These preferences are scheduling instructions; they do not place notification settings inside product workflows.

Every cycle records: starting source/version; issue selected and original requirement IDs; changes; commands and observed results; actual browser/model checks; unresolved findings; release decision and actual public receipts; retrospective; and one exact next action. Current work records belong under `improvement/cycles/`. This revision's initial record is explicitly in progress until its evidence exists.

The heartbeat belongs to this development chat on its configured host. Product users can self-host the application without this automation or System Lab hosting. Application workflow workers, model services and operational records remain separate from the development heartbeat.
