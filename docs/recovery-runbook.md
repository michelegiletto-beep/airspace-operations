# Backup and recovery runbook

Back up the database, complete `runtime/objects/`, permitted source originals, model/experiment lineage and private audit key. The database alone does not contain attachment bytes. Restrict backup access and encrypt off-host storage. Keep an external audit-head checkpoint and document recovery point and recovery time objectives for the deployment.

SQLite: stop writers for a coordinated object-store snapshot, then run `python -m airspace.cli backup --output private-backups/airspace.db`. The SQLite online-backup API preserves a consistent database snapshot. Copy immutable object blobs and the audit key separately. Run `python -m airspace.cli restore --input private-backups/airspace.db --target runtime-restored/airspace.db`; existing targets are refused. Supply the original audit key and verify every organisation with `airspace verify --organisation-id ID`. Check `PRAGMA integrity_check`, attachment hashes and record counts before directing users to the restored service. Never overwrite an active operational instance during a restore drill.

## PostgreSQL credentials and restore procedure

The prepared Compose deployment separates the privileged `airspace_admin` bootstrap/extension/backup identity from the ordinary `airspace` application login. The actual host administrator variable is `POSTGRES_PASSWORD`; the separate ordinary-role variable is `AIRSPACE_DB_APP_PASSWORD`. API and worker `AIRSPACE_DATABASE_URL` values must identify `airspace`, never the administrator. The ordinary role is created with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION` and is not a substitute for a privileged restoration identity.

1. Agree a coordinated checkpoint and stop writers for the database/object-store snapshot. Record database/server/tool versions, application release, organisation/audit heads, object manifests and checkpoint time. Protect the administrator credential and audit key separately from ordinary application configuration and release assets.
2. Run supported `pg_dump --format=custom` as `airspace_admin`, or a separately provisioned backup identity with verified sufficient privileges. Provide connection credentials through a protected PostgreSQL service/password file or the deployment's approved secret mechanism. Never place a password in the command line, shell history, exported log or public CI artifact. Write the binary archive directly to its output file; do not pass it through text-processing/redirection tools that could change its bytes. Preserve checksum and command outcome.
3. Restore into a **new, isolated database/volume**, with compatible PostgreSQL, PostGIS and pgvector versions. Prepare the required extensions using the administrator path and create compatible roles, including the non-superuser `airspace` login with its own private application password. Preserve/review object ownership and grants; do not change application connections to the superuser to work around a failed grant.
4. Run `pg_restore --exit-on-error --single-transaction` using the privileged restoration identity. Restore object blobs and permitted source material from the same checkpoint. Supply the original audit key through protected configuration. An existing-volume environment change does not rerun `deploy/010_application_role.sh` or rotate stored role passwords; use controlled database administration for those changes.
5. Point an isolated API/worker deployment at the restored database using the ordinary `airspace` credentials. Run migrations, every organisation's audit verification, attachment-hash checks, tenant-isolation tests, case exports and resource-reservation checks. Review restored queued/running work and current external facts before resuming workers or directing users to it.
6. Verify role separation explicitly. Application sessions must return `current_user = airspace`. Inspect `pg_roles` for `airspace` and confirm `rolsuper`, `rolcreatedb`, `rolcreaterole` and `rolreplication` are false. Check that extension/privileged maintenance operations use `airspace_admin`, and that the API/worker configuration contains no bootstrap administrator URL/password.
7. Record measured backup/restoration duration, restored counts/hashes, audit outcomes, missing objects, role checks, test outputs and any manual reconciliation. Only then approve the deployment's cutover through its accountable process; retain the prior instance for the agreed rollback period.

These are instructions for the prepared PostgreSQL deployment, **not evidence that a PostgreSQL/Docker drill ran locally**. Those tools were unavailable in the implementation environment. CI and an actual deployment-specific restoration drill must produce their own recorded results before this path is labelled verified. SQLite restoration evidence does not verify PostgreSQL restoration. See [administrator configuration](administrator-handbook.md) for the exact credential mapping.

Worker crash: leases expire and retry within the bounded budget. Inspect job attempts and state, reconcile any stale Running job, then resume only after input review. Paused/cancelled jobs cannot commit a late result. Database interruption must not produce a successful API mutation; transactional records, audit and outbox commit together. No data-recovery action issues aircraft commands.

Evidence integrity failure: restrict the affected object, retain corrupted bytes as investigation evidence, restore from a hash-verified copy and record the incident. Do not regenerate a missing authority receipt or replace an original silently. Record measured restoration duration and the verification command outputs in the deployment's private evidence archive.
