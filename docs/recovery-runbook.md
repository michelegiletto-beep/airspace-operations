## Isolated archive verification

Run `python scripts/verify_archive.py` from the candidate source after packaging. Windows verification selects a unique child of the OS temporary directory. An existing absolute local directory may be selected with `--work-root`; unsafe or overlong roots fail before extraction. Unix keeps the project verification directory. The verifier records canonical paths and keeps installation, isolated database, temporary files and the full pytest suite in that workspace. It does not change Windows settings or the operator database. Preserve failed-run evidence and previous workspaces.

Path preflight is a bounded layout check; it does not replace actual installation and tests. The implementation follows the [Python temporary-directory API](https://docs.python.org/3.13/library/tempfile.html) and accounts for [Windows path constraints](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), checked on 10 November 2026. A successful verification requires every original gate; a preflight result alone is insufficient.


## SQLite input validation in candidate0.3.7

A restore requires an existing non-empty regular SQLite backup with supported Airspace tables, columns and schema markers. Integrity and foreign keys are checked in the same read-only source transaction before a new target is created. Existing targets are refused. Keep the original audit key and verify each organisation audit after restoration; structural validation does not establish audit authenticity, complete attachments or operational readiness.

Earlier0.3.6and preceding CLI versions can create an empty input file and a new empty target when a source path is missing, then report success. They already refuse existing targets. Check source existence, checksum and expected application tables before using an older command; do not treat its success message as recovery evidence. Frozen release bytes remain unchanged.
# Backup and recovery runbook

Back up the database, complete `runtime/objects/`, permitted source originals, model/experiment lineage and private audit key. The database alone does not contain attachment bytes. Restrict backup access and encrypt off-host storage. Keep an external audit-head checkpoint and document recovery point and recovery time objectives for the deployment.

Version 0.3 adds a startup compatibility marker for actor-private companion data. Follow [Upgrading to version 0.3](upgrading-to-0.3.md): stop all older services before migration, verify the restored copy and start only matching new binaries. An already-running old process is not fenced by the marker. Never remove marker 3 or perform an in-place downgrade to 0.2; restore the complete pre-upgrade checkpoint into a separate controlled environment instead.

SQLite: stop writers for a coordinated object-store snapshot, then run `python -m airspace.cli backup --output private-backups/airspace.db`. The SQLite online-backup API preserves a consistent database snapshot. Copy immutable object blobs and the audit key separately. Run `python -m airspace.cli restore --input private-backups/airspace.db --target runtime-restored/airspace.db`; existing targets are refused. Supply the original audit key and verify every organisation with `airspace verify --organisation-id ID`. Check `PRAGMA integrity_check`, attachment hashes and record counts before directing users to the restored service. Never overwrite an active operational instance during a restore drill.

## PostgreSQL credentials and restore procedure

The prepared Compose deployment separates the privileged `airspace_admin` bootstrap/extension/backup identity from the ordinary `airspace` application login. The actual host administrator variable is `POSTGRES_PASSWORD`; the separate ordinary-role variable is `AIRSPACE_DB_APP_PASSWORD`. API and worker `AIRSPACE_DATABASE_URL` values must identify `airspace`, never the administrator. The ordinary role is created with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION` and is not a substitute for a privileged restoration identity.

1. Agree a coordinated checkpoint and stop writers for the database/object-store snapshot. Record database/server/tool versions, application release, organisation/audit heads, object manifests and checkpoint time. Protect the administrator credential and audit key separately from ordinary application configuration and release assets.
2. Run supported `pg_dump --format=custom` as `airspace_admin`, or a separately provisioned backup identity with verified sufficient privileges. Provide connection credentials through a protected PostgreSQL service/password file or the deployment's approved secret mechanism. Never place a password in the command line, shell history, exported log or public CI artifact. Write the binary archive directly to its output file; do not pass it through text-processing/redirection tools that could change its bytes. Preserve checksum and command outcome.
3. Restore into a **new, isolated database/volume**, with compatible PostgreSQL, PostGIS and pgvector versions. Prepare the required extensions using the administrator path and create compatible roles, including the non-superuser `airspace` login with its own private application password. Preserve/review object ownership and grants; do not change application connections to the superuser to work around a failed grant.
4. Run `pg_restore --exit-on-error --single-transaction` using the privileged restoration identity. Restore object blobs and permitted source material from the same checkpoint. Supply the original audit key through protected configuration. An existing-volume environment change does not rerun `deploy/010_application_role.sh` or rotate stored role passwords; use controlled database administration for those changes.
5. Point an isolated API/worker deployment at the restored database using the ordinary `airspace` credentials. Run migrations, every organisation's audit verification, attachment-hash checks, tenant-isolation tests, case exports and resource-reservation checks. Review restored queued/running work and current external facts before resuming workers or directing users to it.
6. Verify role separation explicitly. Application sessions must return `current_user = airspace`. Inspect `pg_roles` for `airspace` and confirm `rolsuper`, `rolcreatedb`, `rolcreaterole` and `rolreplication` are false. Check that extension/privileged maintenance operations use `airspace_admin`, and that the API/worker configuration contains no bootstrap administrator URL/password.
7. Record measured backup/restoration duration, restored counts/hashes, audit outcomes, missing objects, role checks, test outputs and any manual reconciliation. Only then approve the deployment's cutover through its accountable process; retain the prior instance for the agreed rollback period.

These are instructions for the prepared PostgreSQL deployment, **not evidence that a PostgreSQL/Docker drill ran locally**. Those tools were unavailable in the implementation environment. CI and an actual deployment-specific restoration drill must produce their own recorded results before this path is labelled verified. SQLite restoration evidence does not verify PostgreSQL restoration. See [administrator configuration](administrator-handbook.md) for the exact credential mapping.

## PostgreSQL container partial initialisation

The [12 November diagnostic run](https://github.com/michelegiletto-beep/airspace-operations/actions/runs/43319005679) observed an actual incompatible library: the pinned image ran PostgreSQL 17.8, while newly installed PostGIS failed to load with `undefined symbol: heap_datum_check`. Extension initialisation aborted before the `airspace` role was created. Restart then skipped initialisation because the data directory already existed. The administrator readiness probe passed, but API and worker authentication failed. Increasing worker health delays cannot repair this failure.

The candidate replacement pins PostgreSQL 17.12 and rebuilt PostGIS 3.7.0/pgvector 0.8.7 packages together. [PostgreSQL 17.12 release guidance](https://www.postgresql.org/docs/release/17.12/) requires rebuilt C extensions for its new composite-datum checks. Keep the [reviewed image digest and package revisions](../deploy/database.Dockerfile) together when rebuilding. The repaired development source `3f1e338d1d9ebf4ff110a5b6f4a64ba5b519ec8e` passed [actual Linux CI43320866252](https://github.com/michelegiletto-beep/airspace-operations/actions/runs/43320866252), including the deliberately interrupted bootstrap, fresh healthy containers, ordinary-role API/worker, PostgreSQL checks and backup/restoration. Read the exact release-source receipts and perform deployment-specific recovery acceptance before cutover; this isolated test does not repair an existing operator volume.

1. Stop application writers and workers through the deployment's controlled process. Preserve the affected volume, object store, audit key, configuration identity, image digest and private failure evidence. An apparently empty or unhealthy service is not evidence that its volume is disposable. Do not delete volumes, remove PostgreSQL files or rerun bootstrap scripts against the only retained copy.
2. Inspect a protected, consistent copy using the matching administrator tools. Establish whether the extensions and ordinary application role exist, their actual versions and grants, and whether there are application records. Environment changes and container restarts do not complete skipped initialisation. Retain the original state even if a logical backup cannot be produced.
3. Prepare a separate volume from a verified backup or a reviewed copy using a compatible server and rebuilt extensions. Have the database administrator reconcile required extensions, role credentials and grants there. Keep application connections on the restricted `airspace` role; administrator access is reserved for controlled maintenance and restoration.
4. Run the exact production database health command, then the existing API, live worker, PostgreSQL and backup/restoration checks. The database health command authenticates over TCP and loads both extension libraries using read-only SQL; false results, missing privileges, missing extensions and loader errors must remain failures. It does not create roles, install extensions or modify stored data.
5. Compare restored records, object hashes and every organisation's audit chain against the preserved checkpoint before approving any cutover. Keep the prior deployment and rollback evidence. A successful database health result alone does not establish job progress or operational acceptance.

Worker crash: leases expire and retry within the bounded budget. Inspect job attempts and state, reconcile any stale Running job, then resume only after input review. Paused/cancelled jobs cannot commit a late result. Database interruption must not produce a successful API mutation; transactional records, audit and outbox commit together. No data-recovery action issues aircraft commands.

Evidence integrity failure: restrict the affected object, retain corrupted bytes as investigation evidence, restore from a hash-verified copy and record the incident. Do not regenerate a missing authority receipt or replace an original silently. Record measured restoration duration and the verification command outputs in the deployment's private evidence archive.

## Disk exhaustion

Stop publication, ingestion and other work that allocates substantial storage when the volume is full. A failed SQLite startup is not evidence of an empty workspace. Do not delete the database, its write-ahead log, its shared-memory file, the audit key or operational evidence to make the service start. Preserve the stopped database files and key in restricted storage before inspection; never publish those copies.

Recover space through the deployment's approved housekeeping process. Distinguish reproducible temporary build files from authoritative releases, source originals, model artifacts and private records. Check resolved paths and preserve current source and previous release assets. Compression also needs working space and can fail on a full volume. Do not claim that it freed space merely because a compression attribute was set.

After recovering space, run SQLite `PRAGMA integrity_check` and `PRAGMA foreign_key_check` using a read-only connection. Start the matching application version, verify the authenticated actor and organisation, compare API records with persistent data, and verify every organisation's audit chain. Ordinary sign-in creates identity sessions and audit entries; distinguish those from changes to tasks or operational records. Review queued jobs before restarting a worker. Keep publication blocked until sufficient working space exists for the archive, temporary source pack, installation checks and backups.

The 31 October 2026 development-host recovery preserved all 20 existing companion records and verified two tasks against the API, with a valid audit chain. No operational records or model generations were created. This is one recorded recovery, not a deployment reliability guarantee. See the dated disk-recovery, API/data and browser receipts in `release-evidence/v0.3.1-rc.1/`.
