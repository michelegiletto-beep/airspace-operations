# Known limitations and acceptance blockers

## PyPDF dependency advisories found on 1 November 2026

The first 0.3.2 dependency audit failed on three upstream denial-of-service advisories for `pypdf==6.21.3`: [GHSA-5849-834g-hvw5](https://github.com/py-pdf/pypdf/security/advisories/GHSA-5849-834g-hvw5), [GHSA-mfr5-77xh-9j7h](https://github.com/py-pdf/pypdf/security/advisories/GHSA-mfr5-77xh-9j7h) and [GHSA-cggf-277g-3q54](https://github.com/py-pdf/pypdf/security/advisories/GHSA-cggf-277g-3q54). The recorded impacts are infinite loops or excessive memory use while parsing particular PDFs or duplicating PDF objects. The candidate now pins the audit-identified fixed version `6.21.4` in `pyproject.toml`, `uv.lock` and both hashed core/development requirement files. Its installed metadata identifies BSD-3-Clause; upstream copyright, licence conditions and disclaimer remain applicable. The first failed gate and raw audit output are retained in `release-evidence/v0.3.2-rc.1/attempts/pre-security-update/`. Release verification must use the corrected candidate environment and locks, not an older local environment.

Frozen 0.3.1 releases and their recorded dependency scans retain their original bytes and dates. Their `6.21.3` pin is affected by these newly recorded advisories; publishing current documentation does not repair an existing installation. Do not process untrusted PDFs in an affected installation before moving to a reviewed fixed runtime. Generic PDF ingestion remains unavailable in this product, and this review did not establish an exploitable application path, an actual compromise or an operational incident. All other original acceptance, operational-data and domain-review limitations remain open.

The 31 October 2026 media-format guard is verified on the development branch `codex/airspace-media-encoding` at `c6839aeda8276685ea55bae724d90669ae2e9bcd`. It is not part of frozen candidate 0.3.1. That candidate's JPEG under a `.png` filename remains unchanged. A distinct future candidate must supply correctly named media and pass its own installation and release gates. See [publication media validation](release-media-validation.md).

The local Windows volume reached zero free space and caused a development API startup failure. The private SQLite files and key were preserved, integrity/audit checks passed, and existing records were verified after restart. Working space is still insufficient for another package and installation. This host constraint blocks new publication work; it does not change the status of independently retrieved existing releases.

The original master specification is not fully accepted. The engineering candidate contains working services and tests; capabilities.json and REQUIREMENTS_TRACEABILITY.csv preserve the incomplete scope. No stable, certified or production-ready status is claimed.

Software/assurance gaps: Docker/PostgreSQL were unavailable on the local Windows host. Their actual isolated Ubuntu runner verification subsequently passed: application/database containers, worker heartbeat and API-created job,16 PostgreSQL extension/concurrency/dispatch/migration checks and pg_dump/pg_restore. See release-evidence/v0.2.0-rc.1/ci-verification.json. This does not establish production-scale resilience or operator acceptance. Full recurrence/charging optimisation, all SORA steps/calculations, complete route-generation/GIS datasets, automatic retention/erasure, complete route-specific submission templates, interactive offline operation, full occurrence-reporting rules and production-scale failure/performance assurance are incomplete. Local self-hosted SQLite services and restoration are exercised. Schema 3 adds a startup compatibility gate for actor-private companion data. Every older service must be stopped before migration; already-running clients are not fenced. See docs/upgrading-to-0.3.md. Current PostgreSQL/container verification is required for the changed revision; the cited 0.2 run remains historical evidence.

Regulatory/data gaps: the actual corpus has9,833 English structured EASA passages with exact archive/eRules/block anchors. It is a retrieval-date snapshot, with unreviewed consolidated currentness and no approved historical/future applicability timeline. Source retrieval is not legal reconciliation. EUR-Lex direct retrieval returned a challenge/HTTP202. Luxembourg/Italy official pages were fetched but the national packs are not deeply validated. Missing aircraft, personnel, weather, airspace, provider and operational records remain missing. Generic PDF ingestion is unavailable; separate cleared structured XML/HTML ingestion works. There is no proprietary or accepted live operational feed.

Model limitations: three semantic teacher attempts failed and remain preserved. The completed model routes literal shall-language; it does not infer legal obligations. Its machine-label agreement is inferior to a deterministic baseline. No qualified human ground truth or independent time/version holdout exists. Only safetensors and pinned reviewed local model files are loaded; remote code is disabled.

Operational-acceptance requirements: the adopting organisation must establish data rights, operating procedures, competent reviewers, security/identity arrangements, provider contracts, country-specific legal basis and permissions, aircraft/configuration evidence, pilot qualifications and relevant acceptance tests. Provider-specific U-space network integration cannot be completed without actual documented interfaces/access; the release does not claim a universal authorisation API. Internal scheduling/reservations and advisory dispatch checks never activate a provider or aircraft.

Publication states are recorded separately as Prepared, Uploaded, Published and Independently Retrieved. An upload script or expected URL is not evidence of publication. External access is used only where real authenticated permission has been verified. Private runtime databases, keys, correspondence, evidence objects and model-download caches are excluded from public assets.


Revision 0.2 adds genuine local generative orchestration and constrained maintenance/shared-fleet/country/dispatch workflows, with actual execution and isolated fault tests. The local controller uses cooperative generation cancellation and bounded calls; arbitrary native-code preemption, OS process quotas and production queue SLOs require deployment-specific engineering. Cross-country readiness consumes documented instruments and source reviews, not a universal European authorisation API. The50-entry country catalogue is geographical registration, with no automatically validated national pack. The source currentness recheck on 28 October 2026 leaves the original cleared corpus unchanged.

## 0.3.2 development boundary

The local 0.3.2 candidate integrates the reviewed publication guard and mission-planning role guidance. Its own complete release and installation gates remain separate from earlier passing results. No 0.3.2 publication or operational acceptance is inferred from the implementation or focused tests.

New release captures use their own `publication/media/0.3.2-rc.1/` namespace with extensions that match their actual encoding. The publisher checks selected and unselected rasters within bounded byte, file-count and directory-depth limits. It does not rewrite historical media. The frozen 0.3.1 mobile file and release archives must retain their exact bytes. Encoding checks supplement visual, privacy, provenance and rights review; they do not replace those checks.

Other roles receive an explanation and an authorisation-case navigation control while mission-creation buttons remain disabled. This is guidance for an existing permission boundary, not an expansion of privileges or an operating authorisation. The remaining original feature, regulatory, provider and operational-acceptance gaps above remain open.
