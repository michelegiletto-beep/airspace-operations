# Administrator handbook

Create an organisation and initial identity using the CLI in README. Reuse the returned organisation ID for every colleague. Roles: administrator, regulatory, reviewer, planner, pilot, fleet_manager, incident_coordinator, analyst and viewer. The administrator manages configuration; they cannot issue review decisions without a separately assigned reviewer identity. Do not create a second identity merely to evade independence.

Set AIRSPACE_REQUIRE_TWO_REVIEWERS=true for two distinct assigned reviewers. The policy is read from trusted service configuration, never from user-editable case data. Each approval binds the current revision and evidence. Editing a record resets internal approval. The last preparer and original creator cannot approve it. External authority decisions are separately evidenced permission records.

Identity: passwords use scrypt, sessions are opaque, hashed at rest and expire after eight hours. Sign-out revokes the current session. Serve only over TLS outside loopback. Login throttling is process-local; configure gateway-wide throttling for multi-replica deployments. The browser session token is held in sessionStorage, so restrict extensions and protect the workstation.

Enterprise OIDC: set AIRSPACE_OIDC_ISSUER, AIRSPACE_OIDC_JWKS_URL and AIRSPACE_OIDC_AUDIENCE; all URLs require HTTPS. Provision users locally and provide a private AIRSPACE_OIDC_SUBJECTS JSON mapping from verified `sub` to existing user ID. RS256 signature, issuer, audience and expiry are checked. Email or an arbitrary tenant claim cannot enrol or elevate a user. This integration requires real identity-provider acceptance testing before deployment; no provider is connected in the release.

Storage: AIRSPACE_DATABASE_URL selects SQLAlchemy PostgreSQL or SQLite. AIRSPACE_RUNTIME contains database portability files, per-tenant object blobs and private keys. Keep it out of public hosting, source control and model datasets. The audit key must remain stable, private and backed up separately; changing it invalidates historical HMAC verification. Store off-host signed/checkpointed audit heads to detect privileged rewriting and truncation. Objects are content-addressed and checked on download; files are delivered as attachments, never executable pages.

Windows storage paths: run `python -m airspace.cli check` before provisioning a local workspace. This read-only command reports the machine's `LongPathsEnabled` value as true, false or unknown, plus representative evidence and source-ingestion path lengths in UTF-16 code units (Windows characters). Its examples include a 36-character tenant UUID, 64-character content digests and the maximum accepted 100-character source identifier. They are explicit layout calculations; a short result does not prove directory existence, permissions, successful writes, process compatibility or coverage of every temporary/export path. The JSON `schema_version` identifies the software's supported schema; `schema_status` is `Not Inspected`, and the existing database is not inspected or migrated. The command does not initialise a database, create an audit key or change Windows settings.

When long-path support is disabled or unknown, prefer a short private runtime location, for example `C:/SystemLab/Airspace/runtime`, with appropriate access controls. Keep test scratch directories short and isolated as well. Set `AIRSPACE_RUNTIME` consistently for the API, worker and administrative commands. Before relocating an existing runtime, follow the backup/restoration runbook and preserve its database, objects and original audit key; pointing at a new empty directory does not migrate existing records. Recheck the actual deployment's storage and restoration procedures. Python and Windows require platform and process support for ordinary paths beyond the legacy limit; the registry value alone does not verify the running process or external tools. See the [Python Windows path documentation](https://docs.python.org/3.13/using/windows.html#removing-the-max-path-limitation) and [Microsoft path-limit documentation](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation). No global configuration change is performed or required by this software diagnostic.

Containers use two separate PostgreSQL identities. Set the actual variable names from `compose.yaml` and `.env.example` in a private environment; never publish their values.

| Purpose | Database role | Credential and scope |
| --- | --- | --- |
| Database bootstrap, extension initialisation and privileged backup/restoration | `airspace_admin` (`POSTGRES_USER` inside the database service) | Host `POSTGRES_PASSWORD`, passed only to the database container. This is the privileged database-administration credential. |
| Ordinary API/worker connections | `airspace` | Separate host `AIRSPACE_DB_APP_PASSWORD`. `deploy/010_application_role.sh` creates this login with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`. Use this identity and its correctly URL-encoded password in `AIRSPACE_DATABASE_URL`. |

Do not put the administrator identity/password in the API or worker database URL. Both application services receive the ordinary-role URL and private audit key; neither needs the bootstrap password. The database service receives the separate application password solely to initialise the ordinary role. CI secret masking does not replace private deployment-secret handling.

The database image prepares PostGIS and pgvector through `migrations/002_extensions.sql` under the bootstrap administrator, then creates the ordinary role. These initialisation scripts run for a new data volume; changing an environment variable on an existing volume does not rotate a stored role password or rerun initialisation. Perform password rotation as a controlled database-administration task, update the ordinary application's connection secret when applicable, and verify both API and worker reconnection. Do not destroy a persistent volume to apply a credential change.

The current container repair pins PostgreSQL 17.12 with rebuilt PostGIS 3.7.0 and pgvector 0.8.7 packages; the exact image digest and package revisions are in [the database Dockerfile](../deploy/database.Dockerfile). Database readiness now authenticates the ordinary application role over TCP, checks its restricted role and required grants, and executes both extension libraries through a read-only query. A listening server or an administrator `pg_isready` result alone is insufficient. Failed readiness does not modify a volume or repair an incomplete bootstrap. Follow [partial-initialisation recovery](recovery-runbook.md#postgresql-container-partial-initialisation) before resuming a failed deployment; preserve its database, objects and audit key. The replacement image requires its own actual container and restoration evidence before deployment acceptance.

Compose binds the interface to loopback and does not normally expose PostgreSQL. The separate CI override opens a loopback database port for isolated tests. API and worker share the persistent evidence volume; the database has its own volume. Set `AIRSPACE_AUDIT_KEY` privately and consistently for both application services. Build once and test upgrades against a restored copy. Version 0.3 requires schema marker 3 to protect actor-private companion semantics from older application binaries. Follow the [controlled upgrade procedure](upgrading-to-0.3.md), stopping every old API, worker and scheduled client before migration. Mixed-version running services are unsafe. Extension creation remains separate administrator DDL.

After installation, verify that application sessions report `current_user = airspace` and that its four privileged role flags remain false. Confirm that extension initialisation and privileged maintenance use `airspace_admin`. A successful health response alone does not verify this separation. **Docker/PostgreSQL deployment was not executed locally in the implementation environment.** The configuration is prepared; CI/deployment execution and recorded privilege, migration and recovery checks are separate verification gates. See the [backup and recovery runbook](recovery-runbook.md).

Configure readiness checks at /api/v1/health and monitor API5xx, failed jobs, expired leases, ingestion failures, audit verification failures and missing object files. A health response confirms the database probe; it is not source freshness, provider status or operational readiness. Define site-specific SLOs only after measuring representative load. No release target is represented as achieved availability.

The worker's Compose health check runs `python -m airspace.worker_health`. A daemon writes an atomic per-hostname record under `AIRSPACE_RUNTIME/worker-heartbeats`, containing only hostname, process ID and updated UTC timestamp. It refreshes every five seconds while a long model step can occupy the main worker. The check requires that host's live PID and a heartbeat no more than 30 seconds old; missing, invalid, stale and future-dated records fail. This measures process liveness, not queue progress, successful model execution or operational readiness. Monitor job age, failure state and actual completed work separately. The API's HTTP health endpoint and the worker's process health have different scopes.

Worker: allowlisted internal tools run with the initiating user's current role and tenant. Jobs have durable input, attempts, deadline, lease and state. Pause/cancel changes prevent a leased worker from committing its result. Interrupted leases retry up to three times; exhausted attempts become Failed. No workflow can submit to an authority, send external correspondence, change permissions or operate an aircraft. The regulatory-monitor job fetches a registered source into its tenant store, preserves originals/check history and retains failed upstream-check results. Source content changes create owned review tasks through explicit dependencies without overwriting approved cases. Automatic recurring-job scheduling remains a deployment responsibility in this candidate.

Retention/deletion: private data has no automatic retention policy. Define organisational retention and legal holds before loading personal data. The initial product has no verified end-user erasure automation; use a controlled database/object-store process after dependency and audit review. This is an explicit acceptance blocker for deployments requiring automatic erasure. Never remove audit rows through an ordinary user API.
